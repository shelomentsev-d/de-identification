# Техническое задание: приложение для локальной маскировки персональных данных

Рабочее название: PII Mask (макет). Версия документа 1.0, ноябрь 2026.
Статус: для передачи разработчику. База для оценки трудоемкости.

---

## 1. Общие сведения

### 1.1. Назначение

Настольное приложение для macOS, которое перед отправкой документов в
облачные нейросети (Cherry Studio, ChatGPT и аналоги) локально заменяет
персональные и конфиденциальные данные на обезличенные токены вида [ORG_1],
а после получения ответа нейросети выполняет обратную замену токенов на
реальные значения. Приложение работает полностью офлайн после установки.

### 1.2. Основание для разработки

Существует рабочий прототип: консольный скрипт на Python (~350 строк),
используемый в реальной работе с ноября 2026. Скрипт решает задачу, но
требует работы в Терминале, что не подходит для массового использования.
Приложение должно сохранить всю логику ядра прототипа и добавить
графический интерфейс, предпросмотр и управление правилами.

### 1.3. Что уже есть (передается разработчику)

- Скрипт pii_kit.py v1.2: полная логика маскировки и обратной замены.
- Описание форматов, правил, ограничений и типовых ошибок (INSTRUCTIONS.md).
- Набор regex-правил: ИНН, ОГРН, ОГРНИП, СНИЛС, паспорта, расчетные счета
  (сплошные и с пробелами), БИК/КПП (9 цифр), индексы, телефоны РФ, email,
  даты (с «г.» и «года»), ФИО после конструкций «Индивидуальный предприниматель»
  и «ИП» (все падежи, инициалы, двойные фамилии).
- Локальный NER на базе библиотеки natasha (PER, ORG, LOC), работающий
  офлайн после однократной загрузки моделей (~250 МБ).
- Обработчики форматов: docx (с сохранением форматирования через работу
  с runs), xlsx, pptx (слайды, таблицы, группы фигур, заметки докладчика),
  pdf с текстовым слоем (извлечение в md), txt/md/csv.
- Формат ключа замен: JSON {токен: реальное значение} на файл.

Разработчик должен ПЕРЕИСПОЛЬЗОВАТЬ логику ядра, а не переписывать
с нуля. Ядро выносится в отдельный модуль с чистым API (см. раздел 6).

## 2. Термины

- Токен: строка вида [LABEL_N], заменяющая чувствительное значение.
- Ключ замен: файл _keys.json, сопоставляющий токены реальным значениям.
- Сессия документа: жизненный цикл одного файла: загружен, очищен,
  отправлен (вне приложения), ответ восстановлен.
- Правило: regex-шаблон с меткой типа сущности, участвует в маскировке.
- Профиль: именованный набор правил (например, «Договоры», «Резюме»).

## 3. Функциональные требования

### FR-1. Загрузка и очередь файлов

- Drag&drop файлов и папок в окно приложения, также кнопка «Добавить».
- Пакетная очередь: список файлов со статусами (ожидает, обработан,
  ошибка) и прогрессом.
- Поддерживаемые форматы: .docx, .xlsx, .pptx, .pdf, .txt, .md, .csv.
- Валидация на загрузке: несуществующий файл, PDF без текстового слоя
  (скан) со внятным сообщением и подсказкой про OCR, защищенный паролем
  файл, неизвестный формат.
- Имена файлов с пробелами и кириллицей обрабатываются корректно.

### FR-2. Маскировка

- Запуск по кнопке «Очистить» для выбранных файлов или всей очереди.
- Прогресс по файлам, возможность отмены.
- Результат: _clean-файл рядом с оригиналом (или в выбранную папку) и
  ключ замен, привязанный к файлу.
- Статистика по типам сущностей (сколько телефонов, ФИО, ИНН и т.д.).
- Журнал замен: таблица «реальное значение -> токен -> тип», сортировка
  и поиск по ней.

### FR-3. Просмотр и ручная доработка (ключевой экран)

- Сравнение оригинала и очищенной версии: режим «рядом» (split-view)
  для текстовых форматов и табличный список замен для docx/xlsx/pptx
  (рендеринг самих документов внутри приложения не требуется на этапе MVP).
- Подсветка токенов в очищенном тексте.
- Клик по токену показывает реальное значение из ключа (в модальном окне,
  значение не должно попадать в буфер обмена без явного действия).
- Ручная дозамена: пользователь выделяет фрагмент в оригинале и назначает
  тип (PER/ORG/LOC/телефон/свой тип), приложение добавляет токен и
  перезаписывает _clean-файл и ключ.
- Ручной пропуск: пользователь может удалить найденную замену (токен
  возвращается к реальному значению).

### FR-4. Управление ключами замен

- Хранение ключей локально, привязка к исходному файлу и _clean-файлу.
- Список ключей: по какому файлу, когда создан, сколько токенов.
- Экспорт и импорт ключа (JSON), передача ключа другому пользователю
  приложения.
- Опционально (этап 2): шифрование ключей паролем (AES-256, пароль в
  связке ключей macOS Keychain).

### FR-5. Обратная замена (restore)

- Вставка ответа нейросети: текстовое поле или загрузка файла (.txt, .md).
- Выбор ключа замен (по умолчанию предлагается последний использованный,
  если он один в каталоге).
- Толерантный поиск токенов: [ORG_1], (ORG_1), «ORG_1», ORG_1.
- Отчет: сколько замен восстановлено, список токенов из ключа, не
  встретившихся в ответе, с предупреждением о возможном искажении моделью.
- Результат сохраняется как _restored.txt рядом с ответом или в выбранную
  папку.

### FR-6. Редактор правил

- Просмотр встроенных правил (все из прототипа) с возможностью
  включения/выключения каждого.
- Добавление пользовательских правил: regex, метка, описание.
- Валидация regex при вводе с мгновенной подсветкой ошибок.
- Полигон: поле для ввода тестового текста, мгновенный показ того, что
  заменится по текущему набору правил.
- Профили: сохранение набора правил под именем, переключение профилей
  перед очисткой.

### FR-7. Настройки

- Вкл/выкл NER-модуля (natasha): при выключении работают только regex.
- Каталог для _clean-файлов: рядом с оригиналом или отдельная папка.
- Настраиваемый суффикс _clean.
- Автоматическое обновление приложения не требуется.

### FR-8. Сессии и напоминания

- История обработанных документов: файл, дата, статус
  (очищен/ответ восстановлен).
- Предупреждение при попытке очистить несколько файлов с пометкой
  «будут отправлены в разные чаты»: токены нумеруются с 1 для каждого
  файла, смешение документов в одном чате ломает обратную замену.
- Подсказки в интерфейсе на русском языке.

## 4. Нефункциональные требования

- Платформа: macOS 13+, архитектуры Apple Silicon и Intel. Код должен
  допускать портирование на Windows/Linux без переписывания ядра.
- Сеть: после установки приложение не выполняет сетевых запросов.
  Телеметрия отсутствует. Единственное исключение: однократная загрузка
  моделей NER (~250 МБ) при первом включенном NER, с индикатором прогресса
  и возможностью отложить (работа в regex-режиме).
- Производительность: пакет из 10 типовых документов (docx до 50 страниц)
  обрабатывается за время, не превышающее 2 минут на Apple Silicon,
  интерфейс остается отзывчивым, обработка в фоновом потоке.
- Установка: распространение как .app в .dmg (не требуется подпись
  Developer ID на этапе MVP, для внешнего распространения обсуждается
  отдельно).
- Локализация интерфейса: русский.

---

## 5. Требования к безопасности

- Ни один байт содержимого документов не покидает устройство.
- Показ реальных значений только по явному действию пользователя
  (клик по токену), без записи в логи и без автоматического копирования
  в буфер обмена.
- Логи приложения не должны содержать заменяемых значений и токенов.
- Ключи замен хранятся только в выбранных пользователем каталогах;
  опциональное шифрование ключей (FR-4, этап 2).
- Очистка буфера обмена по таймеру (опция, по умолчанию выключена).

## 6. Архитектура и стек

### 6.1. Рекомендуемый стек

Основной вариант: Python 3.11 + PySide6 (Qt6).

Обоснование: ядро прототипа на Python переиспользуется без переноса;
PySide6 дает нативный вид на macOS, кроссплатформенность, зрелые
компоненты (таблицы, прогресс, drag&drop). Лицензия LGPL допускает
внутреннее и коммерческое использование с динамической линковкой.

Альтернатива (обсуждается с заказчиком): Swift + SwiftUI. Плюс: полный
натив. Минус: ядро придется переносить на Swift или оборачивать Python
через PyObjC, что увеличивает сроки на 30-50%.

### 6.2. Структура

- engine/: ядро, перенесенное из pii_kit.py без изменения логики:
  rules.py (regex-правила, профили), ner.py (natasha, lazy-init),
  processors/ (docx, xlsx, pptx, pdf, text), masker.py (координация,
  mapping, counters), restore.py (обратная замена).
  API ядра: mask(path, config) -> MaskResult; restore(text, keys) ->
  RestoreResult. UI не импортирует библиотеки форматов напрямую.
- ui/: экраны (очередь, просмотр, правила, ключи, настройки),
  ViewModel-слой, фоновые worker-потоки (QThread).
- storage/: учет файлов, ключей, профилей правил (SQLite внутри
  ~/Library/Application Support или рядом с документами по выбору).

### 6.3. Тестирование

- Модульные тесты на ядро: не менее 30 кейсов, включая все regex-правила
  и все форматы; эти тесты уже частично существуют в прототипе.
- Интеграционный тест: реальный анонимизированный договор, на котором
  прототип показал пропуски (ИП, ОГРНИП, БИК/КПП, к/с с пробелами,
  индексы, даты с «г.»), приложение обязано замаскировать все те же
  категории.
- Ручной чек-лист приемки: раздел 8.

## 7. Экраны (состав, без макетов)

1. Главная (очередь): список файлов, статусы, кнопки «Добавить»,
   «Очистить выбранные», прогресс, переход к просмотру по клику.
2. Просмотр: журнал замен таблицей (реальное значение, токен, тип),
   текстовое сравнение для txt/md/csv/pdf-извлечений, клик по токену
   показывает значение, кнопки «Дозаменить», «Пропустить», «Отправить»
   (открывает _clean-файл в Finder).
3. Обратная замена: поле/файл ответа, выбор ключа, результат, отчет.
4. Правила: список правил с чекбоксами, редактор regex, полигон.
5. Ключи: список, экспорт/импорт, привязка к файлам.
6. Настройки: NER on/off, каталоги, суффикс.

## 8. Критерии приемки

- AC-1: все форматы из FR-1 обрабатываются, _clean-файл и ключ создаются,
  оригинал не изменяется.
- AC-2: на контрольном договоре (анонимизированная копия из прототипа)
  замаскированы: ФИО ИП в любых падежах, ОГРНИП целиком, БИК, КПП,
  к/с сплошной и с пробелами, ИНН, индекс, все даты вида 15.03.1985,
  телефоны, email; журнал замен совпадает с журналом прототипа
  по составу категорий.
- AC-3: ручная дозамена и пропуск перезаписывают _clean-файл и ключ
  консистентно.
- AC-4: restore восстанавливает ответ с токенами [ORG_1], (ORG_1),
  ORG_1 и честно отчитывается о ненайденных токенах.
- AC-5: приложение не выполняет сетевых запросов после установки
  (проверяется мониторингом сети).
- AC-6: пакет 10 документов обрабатывается без зависания интерфейса.
- AC-7: ошибки (скан PDF, пароль, нет natasha) показывают понятные
  сообщения, не падая.

## 9. Вне рамок MVP (возможные следующие версии)

- Встроенный OCR для сканов (tesseract).
- Англоязычный NER (Presidio, spaCy).
- Плагин/интеграция с Cherry Studio (MCP-сервер поверх того же ядра).
- Рендеринг docx/pptx внутри приложения вместо табличного журнала.
- Шифрование ключей паролем (FR-4, этап 2).
- Windows/Linux сборки.

## 10. Риски

- Качество NER на юридических текстах ограничено (natasha обучена на
  новостях): часть ФИО может пропускаться, глазная проверка и ручная
  дозамена (FR-3) это осознанная компенсация, не дефект.
- Модели natasha скачиваются с внешнего ресурса (github/natasha):
  нужен индикатор и офлайн-режим.
- python-pptx не обрабатывает диаграммы и вложенные объекты: ограничение
  документируется в интерфейсе.

## 11. Этапы

- Этап 1, MVP (оценка 2-3 недели): FR-1, FR-2, FR-3 в объеме журнала

- Этап 3 (опционально): шифрование ключей, OCR, интеграции.
